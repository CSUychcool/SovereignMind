# llm-server（llm-chat）演进需求文档

- 版本：v0.8（需求基线 + 选型结论 + P1 + 产品化/部署层 + 上下文透明）
- 日期：2026-09-10
- 状态：需求整理完成，D1~D10 选型已交互拍板（见 §28），未开始开发
- 范围：在现有 C++17 自研 HTTP 服务器 + Ollama/vLLM 本地大模型 + MySQL 的架构上，规划演进需求。
- 说明：v0.6 明确"两条召回路径"的区分——需求十八（新增 P1）只针对**路径B：历史会话召回**（现有 searchMessages LIKE），与需求四的**路径A：文档召回**（LLM 选 md）分开表述；原有需求一~十七编号保持不变。v0.7 新增**产品化/部署层**需求十九~二十三（端侧设备接入 API、移动/桌面客户端、软件内 TCP 内网穿透、Docker 化部署），详节见 §20~§24。v0.8 新增**需求二十四 上下文全透明**（§25）——私有化定位的核心竞争点：云端厂商受防逆向/保密约束不向用户展示完整上下文，而本产品自托管、数据全在本机，可以把"看得见的上下文"做成独特卖点。

---

## 0. 当前架构一句话回顾

浏览器 `web/index.html` → `:9000` → `net`(双线程池+fd移交) → `route/Router`(集中鉴权) → `handler`(4个，解析+编排) → `service`(Auth/Conversation/LlmGateway/ModelService/TokenCounter) → `db`(MySQL) + 上游 Ollama/vLLM。

当前能力：登录会话、多对话 CRUD、token 预算装历史(P0)、滚动摘要(P1)、清上下文(P2)、关键词召回(P3)、SSE 流式对话、模型切换。

## 2. 需求一：压缩节流改为方案B（连压至 hasOlder=false）

- **优先级**：1（阶段0，P1）
- **背景**：当前 `ChatHandler::tryCompaction` 有 `messagesSince < 20` 节流（`AppConfig::summaryMinNewMessages`），溢出态约每 10 轮问答才压缩一次，摘要滞后。
- **目标**：溢出时持续压缩直到未压缩活跃段可装进预算（hasOlder=false），摘要贴合当前。
- **功能需求**：
  - FR1-1 取消/放宽节流门槛（可配置，默认关闭）。
  - FR1-2 `tryCompaction` 单请求内循环：每压一批重算溢出，溢出继续，`hasOlder=false` 或达最大迭代数停止。
  - FR1-3 最大迭代上限（如 5 批）防小预算死循环。
  - FR1-4 保留 `summary_upto` 语义与 `clearContext` 重置行为。
- **技术方案要点**：仅动 `ChatHandler.cpp` 的 `tryCompaction`；不改 DB 结构；`hasOlder` 每批后经 `loadHistoryByTokens` 重算。
- **依赖**：无。
- **验收标准**：溢出会话单请求后消息表收敛到预算可装规模；无死循环；节流开关可调。
- **工作量**：1–2 人日。

## 3. 需求二：文档上传 → RAG 知识库 + RAG GRAPH

- **优先级**：2（阶段1，主工程，P1）
- **背景**：当前只有对话内 P3 关键词粗召回，无外部知识注入。
- **目标**：文档上传→切块→本地向量化→入库；问答时语义检索；入库**固定生成** RAG GRAPH，暴露接口让用户可选是否在回答中使用（图固定生成，用不用可选）。
- **功能需求**：
  - FR2-1 文档上传（txt/md/pdf/docx），解析纯文本。
  - FR2-2 切块：按段落/长度，chunk 大小与重叠可配。
  - FR2-3 embedding 本地模型向量化，`RAG(document_id, chunk_id, content, vector, meta)` 入库。
  - FR2-4 知识库 CRUD。
  - FR2-5 检索：向量 top-k 语义召回，可混合关键词兜底。
  - FR2-6 GRAPH 入库时强制生成：实体/关系抽取，存图。
  - FR2-7 使用开关：请求级 `use_graph` + 全局默认；构图行为不受开关影响。
  - FR2-8 回答增强：检索片段+（启用时）图邻域实体注入 system 参考资料段。
  - FR2-9 引用来源标注（可选，P2 内）。
- **技术方案要点**：选型结论见 §28（D1~D3）。
- **依赖**：无（为需求四、十八提供检索基座）。
- **验收标准**：上传→命中文档内容可溯源；GRAPH 未启用也生成；开关有可观察差异。
- **工作量**：12–18 人日。

## 4. 需求三：语音输入转文字（ASR）+ 朗读回答（TTS）

- **优先级**：3（阶段1，独立并行，P1）
- **目标**：录音→转文字进对话；回答朗读（支持流式逐句）。
- **功能需求**：
  - FR3-1 前端录音（MediaRecorder）+ 录音 UI（开始/结束/取消/音量提示）。
  - FR3-2 ASR 接口 `POST /api/asr`：音频→中文文本→回填输入框。
  - FR3-3 TTS：回答完成后手动/自动朗读；SSE 增量逐句读。
  - FR3-4 朗读控制：暂停/继续/停止/语速/开关。
- **技术方案要点**：快路径=浏览器 Web Speech API（Chromium 识别走谷歌、国内可能不可用；合成用 OS 离线语音可用）；本地路径=whisper.cpp/faster-whisper(ASR) + piper/edge-tts(TTS)。结论：v0 浏览器 API 原型，v1 本地 whisper+piper 替换 ASR（§28 D4）。
- **依赖**：无。
- **验收标准**：录音→中文转文字可用；回答可朗读可中断；本地路径断网可用。
- **工作量**：原型 1–2 人日；本地引擎 8–10 人日。

## 5. 需求十八 (新，P1)：历史会话召回升级为向量匹配

- **优先级**：1（P1，阶段1，随 需求二 批量交付）
- **背景（先区分"两条召回路径"）**：
  - **路径A·文档召回（需求四 温路径文档）**：召回对象是"注意事项/结论"等 md 文档，用**大模型判断**选择哪些片段拉入上下文（预算富余才触发）。本次需求**不涉及**它。
  - **路径B·历史会话召回（本需求）**：召回对象是**对话历史消息**（含已被滚动压缩进摘要的旧会话内容）。现状代码**已实现**：`searchMessages` 的 `LIKE '%kw%'`（`ConversationService.cpp:153-170`）+ `ChatHandler::joinKeyboardRecall`（即上下文管理 P0~P3 阶段中的 P3，代码注释亦称 P3）。缺陷：无中文分词、纯中文提问整句当关键词，字面命中质量差。
- **目标**：只把**路径B（历史会话召回）**从"关键词粗召回"升级为"向量语义召回"；需求二 落成的 faiss + embedding 基建复用，LIKE 保留作兜底。
- **功能需求**：
  - FR18-1 **消息增量向量化**：`appendMessage` 落库时生成 embedding，写入 faiss 索引（限定 conv_id 维度）+ MySQL 记录向量；存量消息批量回填一次。
  - FR18-2 **向量召回**：提问 embed → 该 conv_id 范围内 faiss 检索 top-k → 回填窗口外相关旧消息；注入逻辑（预算守卫、数量上限、时间正序）沿用现状，只换召回通道。
  - FR18-3 **LIKE 保留为兜底**：向量命中数/相似度低于阈值时回退 LIKE；或请求级开关切换两种模式（默认向量）。
  - FR18-4 复用 需求二 的切块/embed/检索抽象，不新建基础设施。
- **技术方案要点**：faiss 用 conv_id 元数据过滤；embedding 同步走 Ollama `/api/embed`（§28 D1）。旧 LIKE 路径保留作水泵回退，避免向量召回质量问题引入回归。
- **依赖**：需求二（faiss + embed 基建先期落成）。
- **验收标准**：同一提问下向量召回对相关旧消息命中优于 LIKE；严格 conv_id 隔离不串会话；注入预算守卫/上限行为不回归。
- **工作量**：3–5 人日（依托需求二基建）。

## 6. 需求六：Agent 自驱动循环（ReAct）

- **优先级**：4（阶段2，地基）
- **背景**：参考 Claude Code 的 ReAct 模式——响应含 `tool_use` 则执行并回填继续，无则返回最终答案。当前 `/api/chat` 为单轮 SSE 直转，无工具执行。
- **功能需求**：
  - FR6-1 循环协议：messages→模型→`tool_calls`→执行→回填→重入；无→返回最终文本。
  - FR6-2 LlmGateway 扩展：流式/非流式工具调用（兼容 OpenAI 与 Ollama/vLLM 格式）；流式呈现"正在执行"。
  - FR6-3 `max_agent_iterations` 上限（默认 10），超限强制结束并提示。
  - FR6-4 工具异常回填错误文本续跑，不中断。
  - FR6-5 循环内上下文累积，不污染 messages 表（仍只存 user/ai）。
  - FR6-6 流式 `[DONE]` 前处理完 tool_calls。
- **技术方案要点**：前置验证 qwen2.5 在 Ollama/vLLM 的工具调用支持；若不支持退化为"文本指令式工具"（模型输出 JSON 指令，服务端解析执行）。独立 `service/AgentLoop`，与单轮路径并存（agent 开关）。结论：原生 tool_calls 优先 + 文本指令式兜底（§28 D5）。
- **依赖**：无（上游能力验证项）。
- **验收标准**：端到端"问→调工具→拿结果→最终回答"；超限兜底；历史表不污染。
- **工作量**：8–12 人日。

## 7. 需求七：Tool 接入 + 按需注入工具说明

- **优先级**：5（阶段2，紧随需求六）
- **背景**：参考 Claude Code——官方工具及用法写入文档；循环中**正使用/已知用法**的工具不重复导入说明，省 token。
- **功能需求**：
  - FR7-1 `ToolRegistry`：id/名称/描述/参数 schema/执行函数/权限标识。
  - FR7-2 工具说明文档 `tools.md`：官方工具与用法全集。
  - FR7-3 **按需注入**：循环内已用/已知工具只注入名称，未用过才注入完整 schema。
  - FR7-4 工具安全分级（只读/写/危险），供需求十一、八使用。
  - FR7-5 工具结果规范化 JSON，结果大小上限。
- **技术方案要点**：与 AgentLoop 联动；schema 以 JSON（OpenAI 格式）生成并限大小/数量；"已知用法"追踪=循环内已见集合。
- **依赖**：需求六。
- **验收标准**：同循环二次调用不重复注入说明；结果回填正确。
- **工作量**：5–7 人日。

## 8. 需求十 (新)：工具执行沙箱/隔离

- **优先级**：6（阶段2，与工具执行同批落地）
- **背景**：服务拟开放文件/命令类工具，且将提供 YOLO/MCP。在**服务器**上以宿主用户权限执行任意命令，危害远大于 Claude Code（后者在用户本机）。这是服务端 Agent 化的安全底线。
- **目标**：所有工具执行（尤其 Shell/文件/DB 写）运行在隔离沙箱，与服务器宿主隔离。
- **功能需求**：
  - FR10-1 沙箱边界：文件系统、网络、进程资源三类隔离（受限读写、网络白名单、CPU/内存/时间配额）。
  - FR10-2 执行后端：子进程 + seccomp/rlimit（轻）或容器（docker/podman）工作区（重）；统一 `SandboxRunner` 接口。
  - FR10-3 超时/输出上限/退出码规范化；泄漏/逃逸事件日志+熔断。
  - FR10-4 工作区卷映射与清理策略（临时目录自动回收）。
- **依赖**：需求七（工具开始执行）。
- **验收标准**：注入危险命令（删根/连外网/死循环）被约束；正常工具操作不受影响。
- **工作量**：8–12 人日（后端选型见 §28 D6）。
- **备注**：已拍板为 docker 容器工作区（§28 D6）；若阶段2 开工时 WSL 下 docker 不可用，降级"专用受限用户 + seccomp"轻方案（隔离度有限，工作量减半）。

## 9. 需求十一 (新)：权限规则系统 allow/deny/ask

- **优先级**：7（阶段2-3）
- **背景**：Claude Code 对每次工具调用具备许可分级（允许/拒绝/询问），规则可持久化。当前方案只有"登录 or YOLO"两级，缺少粒度。
- **目标**：工具/操作的轻量权限规则引擎，是自动执行的基础，也是 YOLO 的规则来源。
- **功能需求**：
  - FR11-1 三级策略：`allow`（自动执行）/ `ask`（逐次询问）/ `deny`（禁止）。
  - FR11-2 规则匹配：工具类型 × 参数模式（路径前缀/命令名等）→ 策略；支持通配与覆盖顺序。
  - FR11-3 规则持久化与管理接口（`/api/control/permissions`），按用户粒度。
  - FR11-4 一次询问可"本次允许/记住允许/本次拒绝/记住拒绝"。
  - FR11-5 与 YOLO 联动：YOLO = 所有 `ask` 视作 `allow`（危险类除外）。
- **依赖**：需求六、七（有工具才有权限）。

## 16. 需求四：温路径文档（自动生成 md + 预算富余时拉入上下文）

## 20. 需求十九 (新)：端侧 AI 设备接入 API（局域网共享端侧模型）

- **目标**：为端侧设备提供轻量、低耦合的消息与能力 API，让"一台电脑，全家/全屋共享同一个大脑"成为标准形态。

- **技术方案要点**：纯服务端 API 扩展，复用现有 `route/` 鉴权框架新增"设备 token"维度；WebSocket 推送可复用现有 SSE 机制改造。
- **依赖**：无（基于现有 Auth 与对话能力）。
- **验收标准**：LAN 内设备经网关免登录调用对话/检索；吊销 token 即时失效；设备会话与网页会话数据隔离。
- **工作量**：5–8 人日。

## 23. 需求二十二 (新)：软件内 TCP 内网穿透（免备案）

- **优先级**：22（阶段5）
- **背景**：Web 形态的对外访问，内网穿透服务**只对备案过的网址提供 HTTP/HTTPS**；一旦打进 App/桌面客户端，就可以走 **TCP 形式的内网穿透**，**无需备案网页**即可在外网使用——这是"软件形态"相对"网页形态"的天然优势。
- **目标**：客户端内置 TCP 穿透通道，非局域网访问免备案、免 HTTP 站点依赖。
- **功能需求**：
  - FR22-1 穿透模式：内置 frp client 连接自建/指定 frps；P2P（Tailscale/WireGuard）作为备选。
  - FR22-2 透明切换：客户端优先探测局域网直连，失败自动切穿透通道（需求二十/二十一 共用同一连接逻辑）。
  - FR22-3 配置管理：穿透服务器地址/token 在 App 内配置；服务端给出 frps 部署与安全加固文档。
  - FR22-4 安全：穿透通道加密（TLS/噪声协议）＋服务端访问控制；仍遵循现有 `/api/*` 需登录约束。
- **技术方案要点**：frp client 以子进程/动态库形式集成进客户端；P2P 备选。Web 版维持现有 HTTPS 网页穿透路径不变，两者并存。
- **依赖**：需求二十/二十一（客户端形态）。
- **验收标准**：外网下 App 经 TCP 穿透成功对话；局域网直连不受影响；无备案约束。
- **工作量**：5–9 人日。

- **技术方案要点**：上游模型（Ollama/vLLM）默认跑宿主或独立容器，镜像保持轻量、不含模型权重。
- **依赖**：无（可与主线并行）。
- **验收标准**：`docker compose up` 一键全栈；重启后数据不丢失。
- **工作量**：3–5 人日。

## 25. 需求二十四 (新)：上下文全透明——UI 实时展示"当下拼接的上下文"（核心竞争点）

- **优先级**：24（阶段1；核心竞争点，可先行）
- **背景**：Claude Code 等云端厂商**不会把完整上下文展示给用户**——一方面有技术保密考量：避免其他厂商通过**输入输出倒推其系统/提示工程结构**；也正因如此，甚至存在**在网络层注入干扰语句防抓包逆向**的做法。这是云端保密立场下的必然取舍。而本产品**私有化自托管**：用户即系统所有者，没有"被逆向"的顾虑——**可以在 UI 界面实时展示当下拼接的上下文，实现完全透明化**。云端不敢给的，我们全给，**透明本身就是卖点**。
- **目标**：每次会话，用户在 UI 上**实时看到当前拼接的上下文**——发给模型的每一段都看得见、标得清来源，上下文管理不再是黑盒。
- **功能需求**：
  - FR24-1 **实时拼接视图**：发送前/生成过程中，前端面板**实时刷新**当前即将发给模型的完整上下文——system 静态/动态块、消息历史（区分**原样部分**与**被压缩部分**）、滚动摘要、向量召回片段、RAG/图谱邻域（`use_graph`）、温文档，逐段可展开查看。
  - FR24-2 **逐段来源标注**：每段标注来源——历史原消息 / 摘要压缩 / 语义召回 / RAG 引用 / 图谱邻域 / 温文档 / system 静态块 / system 动态块；点击可跳到对应原文位置（原消息/原文档段）。
  - FR24-3 **Token 实时细账**：每段 token 数实时展示，与现有用量条同一口径——"预算装历史"的裁剪/压缩过程**所见即所得**（压缩前后对比）。
  - FR24-4 **与发送定格同步**：点击发送瞬间拼接状态定格为"本次请求上下文"，流式回答期间持续展示，可随时回看"这条回答是吃了什么上下文生成的"。
  - FR24-5 **面板开关**：可折叠/关闭；性能或隐私敏感时可降级为仅显示统计（不载入完整内容）。
- **技术方案要点**：服务端在上下文组装完成处（复用现有 token 记账/`loadHistoryByTokens` 逻辑）把"将发送的拼接上下文"通过 **SSE 专有事件**（如 `event: context`，首 token 之前先推）或专门接口推给前端；前端渲染"上下文浏览器"面板，与发起请求同频刷新。不动模型接口与对话主链路。
- **依赖**：现有上下文管理（预算装历史 / 滚动摘要 / 向量召回）+ 需求二（召回溯源元数据）。
- **验收标准**：任意一次对话发起时，UI 实时显示与实际发给模型一致的拼接上下文；逐段来源可追溯；面板关闭后对话功能不受影响。
- **工作量**：5–8 人日。

## 28. 选型结论（2026-09-09 已交互拍板）

> D1~D10 全部决策收敛如下；结果同步 repo 与 Obsidian。

| # | 决策项 | 结论 |
|---|---|---|
| D1 | embedding | **nomic-embed-text，常驻 Ollama `/api/embed`，与聊天后端(ollama/vllm 双配置)解耦**。vLLM 名义支持 nomic(/v1/embeddings) 但有 serving 报障且需独立 vLLM 实例，不采用 |
| D2 | 向量库 | **faiss 嵌入 C++ 进程内**；chunk 元数据存 MySQL（RAG 表），faiss 索引落盘 |
| D3 | RAG GRAPH | **LLM 批量抽取 × MySQL ENTITY/EDGE 邻接表**（入库时后台生成，用不用由请求 `use_graph` 开关决定） |
| D4 | 语音 | **v0 浏览器 Web Speech API 原型 → v1 whisper.cpp/faster-whisper + piper 替换 ASR**；TTS 可保持系统/浏览器合成 |
| D5 | 工具调用 | **原生 tool_calls 优先，文本指令式（JSON 指令）退化兜底**；LlmGateway 支持双格式解析 |
| D6 | 执行沙箱 | **docker 容器工作区（SandboxRunner 统一接口）**；前置：M3 开工前确认 WSL 下 docker 可用，不可用则降级受限用户+seccomp |
| D7 | 答案缓存 | **默认关·窄命中**（只缓存无时间依赖通用问题，准确优先） |
| D8 | 危险操作 | **默认危险三类：DB 写、文件删改、外发/安装执行；其余默认放行** |
| D9 | MCP 传输 | **v0 只做 stdio（本地子进程）**；SSE/WS 远程后续补 |
| D10 | 联网检索出口 | **直连当前 NAT 主机外网**；frp 仅作"从外网访问本服务"的穿透选配，与联网检索无关 |
